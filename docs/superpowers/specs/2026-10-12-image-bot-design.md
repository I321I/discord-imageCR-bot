# 動畫截圖圖庫 bot 設計

日期：2026-10-12（2026-10-16 修訂：OCR 改為 RapidOCR，並同步實作期間的設計變更，見文末「實作期間的設計變更」）

## 目的

使用者常用帶字幕的動畫截圖當梗圖回應。找圖時記得的線索可能是作品名、角色、字幕內容或某個關鍵字。這個 bot 讓伺服器把特定頻道當成「圖片來源頻道」（圖庫），丟進去的圖片會自動整理成「圖片＋圖片訊息」，使用者之後在任何地方用指令輸入關鍵字，就能找到並貼出那張圖。

成功的樣子：在圖庫頻道丟圖後不用做任何事就能被搜到；搜尋時打幾個字就有提示，選了就貼出圖。

## 目標 / 非目標 / 反目標

- 目標：自動整理圖片、免費辨識作品與字幕、可修改、跨伺服器搜尋、重啟不遺失設定。
- 非目標：辨識角色（沒有免費又準的方案，角色留給使用者填）；重新整理頻道裡的舊圖片。
- 反目標：
  - 需要付費 API（全部要免費）。
  - 辨識失敗時卡住或吞掉圖片（失敗也要照常發出，並清楚標示）。
  - 用檔案存設定（設定要存成 Discord 訊息）。
  - 覆蓋使用者已填的資料。

## 現況

- Go + discordgo，主程式 `bot.go`。`.env` 有 `TOKEN`、`SERVER_ID`。
- 已有 `/channel add | remove | list | id`（伺服器安裝指令），頻道存在記憶體 `guilds_channels`，重啟會消失。
- `/search`（使用者安裝指令）只有宣告，沒有內容。
- 現有程式的已知問題：`handdleChannelList`、`handdleChannelRemove` 用全域的 `GuildId`（`SERVER_ID`）而不是 `i.GuildID`。資料存放方式要改，這部分可以一起修。

## 名詞

- **圖片來源頻道**：被 `/channel add` 設定的頻道。
- **圖片訊息**：機器人發的「一張圖＋固定格式文字」訊息。
- **舊圖片訊息**：在圖片來源頻道裡，**頻道被設為來源之前**由使用者發的、帶圖片的訊息。
- **設定時間點**：`/channel add` 當下的時間（用 snowflake 表示），和頻道一起存在儲存頻道。訊息 ID 比它大，就是設定之後發的。
- **儲存頻道**：開發者指定、用來存設定資料的頻道。

## 一、伺服器端

### `/channel add | remove | list`

保留現有行為，改成（`/channel id` 已於實作期間移除，改用 Discord 開發者模式複製頻道 ID）：
- 只在伺服器中可用，對象是下指令的那個頻道。
- 每次 add / remove 成功，就把最新的完整資料寫到儲存頻道（見「四」）。
- 權限：預設需要「管理伺服器」權限（`default_member_permissions`），伺服器管理員可以在 Discord 設定裡調整。**（建構者的判斷）**

## 二、圖片來源頻道的自動處理

使用者在圖片來源頻道發了帶圖片附件的訊息時：

1. 先把每張圖都辨識完，**全部辨識完成後才發**圖片訊息（使用者決定。不用「先發再補」）。trace.moe 有並行限制，請求要排隊。
2. 每張圖片各發一則圖片訊息，**重新上傳圖片檔**（原訊息刪除後，原本的 CDN 連結會失效）。
3. 所有圖片都發完之後，刪除使用者的原訊息（bot 需要「管理訊息」權限）。
4. 原訊息裡的文字放進每張圖的「關鍵字」，以免文字因刪除而遺失。**（建構者的判斷，使用者未反對）**
5. 純文字訊息不處理，保留原狀。

### 哪些訊息要處理（使用者決定）

- PNG、JPG、WEBP 處理；GIF 也算圖片，用第一個畫面辨識。
- 訊息裡只要有非圖片的附件（影片、檔案等），**整則不處理、不刪除**。
- 圖片網址訊息（2026-10-19 起，取代原本「貼圖片連結或 embed 的訊息不處理」，規則見 `docs/plans/2026-10-19-image-url.md`）：
  訊息文字中的圖片網址（路徑副檔名為 .png/.jpg/.jpeg/.webp/.gif，或 Discord 對它的預覽為圖片）每個算一張，與附件一起編號（附件在前、網址在後）；一般網頁連結照舊不處理。
  新訊息下載網址圖片（防 SSRF：只連公開位址的 80、443，25MiB 上限）走一般流程、重新上傳，任一張失敗就一張都不發、保留原訊息並加 ❌；gifv 動圖連結新訊息不處理。
  只含圖片網址（沒有附件）的訊息以「設定時間點」與「圖片網址功能上線時間點」（存在設定資料 `url_since`）較晚者區分新舊；更早的只收進搜尋，`/search` 確認圖床上的圖片還在後直接貼出網址。

### 離線補處理（使用者決定）

機器人啟動、建索引時，在圖片來源頻道遇到使用者發的、符合上述條件的圖片訊息：
- 訊息 ID 晚於該頻道的設定時間點：當成離線期間漏掉的，照正常流程補處理。
- 早於設定時間點：是舊圖片訊息，只供搜尋。

### 圖片訊息格式

欄位順序固定，留空的欄位放在最後：

```
作品：葬送的芙莉蓮
圖片文字：這就是人類啊
角色：
關鍵字：
上傳者：@某人
```

- 最後一行「上傳者」標註原發文者（mention），不算進四個欄位，不能編輯，搜尋時也不比對。（使用者決定）
- 作品：用 trace.moe 免費 API 判斷。
- 圖片文字：用 OCR 判斷。
- 角色、關鍵字：留空，由使用者填寫。
- 多個值一律用「、」分隔。使用者輸入的 `，`、`,` 等分隔符號，機器人都統一換成「、」。圖片文字不拆分，多句字幕用換行。
- **辨識失敗**（找不到、額度用完、API 出錯）：該欄寫成 `⚠️ 辨識失敗`，圖片照常發出。

### 辨識

- **作品**：trace.moe（免費額度有每月上限，也有並行限制）。結果相似度太低時視為失敗，門檻由建構者決定。
- **圖片文字**：RapidOCR（PaddleOCR 手機版模型，onnxruntime），中文模型＋日文辨識模型，中文結果以 OpenCC `s2twp` 轉為台灣繁體。字幕大多是繁中，少數是日文、英文、簡中。
  - **改版（2026-10-13）**：原本採用 Tesseract（`chi_tra+chi_sim+jpn+eng`），真實字幕截圖命中率只有 21%／10%／0%；改用 RapidOCR 後在 Raspberry Pi 3B 上實測三張皆 100%。
  - 先辨識圖片下方 35% 的字幕區（縮到寬 640）；字幕區沒讀到字、讀到直書文字框、或圖片高 > 寬（漫畫）時，改辨識整張（縮到長邊 1280）。
  - 每個文字框都跑中文與日文辨識（偵測只做一次），日文結果含平假名或片假名時採用日文結果，否則採用中文結果；一張圖超過 100 個文字框時只用中文模型。
  - 直書漫畫對話框：同一對話框的各欄接成一行（由右至左），不同對話框換行。

## 三、圖片訊息的修改

都是**訊息右鍵選單指令**（Message context menu），只對機器人發的新格式圖片訊息有效；對其他訊息使用時，回覆一則只有使用者看得到的說明。

### 「編輯圖片訊息」

- 跳出一個表單，有作品、圖片文字、角色、關鍵字四個欄位，**預先填入目前的值**，全部選填。
- 送出後機器人編輯該則訊息，分隔符號正規化為「、」。
- 欄位如果是 `⚠️ 辨識失敗`，預填時可以留空或保留原文字，由建構者決定。

### 「重新辨識」

- 只重跑標了 `⚠️ 辨識失敗` 的欄位，成功就填入，失敗就保留標記。
- 其他欄位一律不動，包括使用者填的角色、關鍵字，以及之前已辨識成功的欄位。
- 沒有失敗欄位時，回覆一則只有使用者看得到的提示，說明不需要重新辨識。
- 重新辨識需要原圖：從該則圖片訊息的附件取得。

### 權限

看得到該圖片來源頻道的人都能使用（判斷方式與「四」的可用條件相同）。

## 四、使用者端（使用者安裝 App 指令）

### `/search`

- 可以在任何伺服器或私訊使用。
- 有一個字串參數，使用 **autocomplete**：輸入時比對使用者可用頻道裡的所有圖片，最多顯示 25 筆（Discord 上限）。
  - 新格式圖片訊息：比對作品、圖片文字、角色、關鍵字四個欄位，提示顯示「作品｜圖片文字」（超過 100 字截斷）。
  - 舊圖片訊息：比對整段訊息文字，提示顯示文字開頭。一則舊訊息有多張圖時，每張圖各算一筆。只有圖、沒有文字的舊訊息不收錄。
- 送出後，機器人在目前聊天室**公開發出那張圖**，只發圖片，不附圖片訊息。
- 排序方式、比對方式（不分大小寫、部分符合等）由建構者決定。

### 選擇自己的圖片來源頻道

- 一個使用者安裝指令（名稱由建構者決定），列出「使用者所在的伺服器中，被設為圖片來源的頻道」，用勾選的方式（select menu，可多選）選擇要用哪些。
- 沒選過的使用者，預設使用全部可用頻道。
- 「可用」的條件：該頻道被設為圖片來源、使用者是那個伺服器的成員，**而且使用者看得到該頻道**（View Channel 權限，要把身分組與頻道權限覆寫都算進去；2026-10-15 起另需 Read Message History）。這個規則同時套用在 `/search`、勾選指令列出的頻道、右鍵指令。（使用者決定）
- 成員資格與權限用 REST 查詢，結果**快取幾分鐘**，避免 autocomplete 逾時（3 秒限制）或撞到速率限制；不開啟 Server Members 特權 intent。代價是使用者離開伺服器或身分組被改後，可能要幾分鐘才失效。（PM 的判斷，使用者已同意）
  - 快取：記憶體表，key 為（guildID, userID），value 為成員的身分組或「非成員」（REST 回 404 也快取）加上查詢時間，預設 5 分鐘過期（實際長度由建構者決定），用 mutex 保護。
  - 頻道是否可見不快取：身分組與頻道權限覆寫來自 gateway state（需加開 `IntentsGuilds`），現算（discordgo v0.29.0 未公開 `MemberPermissions`，改為自行移植其計算方式），所以頻道權限的變更會立即生效。
  - 快取沒有命中的伺服器，同時發 REST 請求，以趕上 autocomplete 的 3 秒限制。
- 勾選結果存到儲存頻道。

## 五、儲存頻道（開發者）

- `.env` 新增 `STORAGE_CHANNEL_ID`。必須放在 env，因為重啟時要先知道去哪裡讀。
- 「開發者」= Discord 開發者後台這個 application 的擁有者（如果是團隊，則為團隊成員），啟動時查詢。
- 開發者專用指令：查看目前的儲存頻道、手動重新讀取、手動寫回最新資料。只有開發者能用，其他人使用會被拒絕。
- 資料用 JSON，存成**訊息內容**，不用檔案。內容包含：
  - 各伺服器的圖片來源頻道與各自的設定時間點（guildID → channelID → 設定時間點）
  - 各使用者勾選的頻道（userID → channelIDs）
  - 格式版本號
- 任何變動（`/channel add/remove`、使用者勾選）都發一則新的完整版本。啟動時讀最新版本。
- 超過 2000 字時拆成多則，標上「1/3」這類編號與同一個版本識別，讀取時拼回去。只讀到不完整的一組時，往前找上一個完整版本。

## 六、搜尋索引

- 啟動時讀完所有圖片來源頻道的訊息歷史，在記憶體建立索引：
  - 機器人自己發的圖片訊息：解析四個欄位。
  - 使用者發、帶圖片的訊息：早於設定時間點的當成舊圖片訊息；晚於的補處理（見「二」）。
- 之後新增、編輯、重新辨識、`/channel add/remove`，都即時更新索引。
- 圖片訊息本身就是資料來源，不另外存一份。

## 七、部署（使用者決定）

- 用 Docker 部署，提供 `Dockerfile`（單一映像、單一容器）。部署目標為 **Raspberry Pi 3B**（linux/arm64，905MB RAM＋zram）。
- OCR 由同一容器內常駐的 Python 子行程（`ocr/ocr_worker.py`，RapidOCR＋OpenCC）執行，Go 以 stdin/stdout 每行一個 JSON 溝通；第一張圖來時才啟動，閒置 5 分鐘自動結束以釋放記憶體。映像內含 Python 依賴（版本鎖定）與日文模型（建置時下載並驗證 sha256）。
- OCR 是可替換的介面，測試時用假的實作替換，`go test` 不需要 Python 或 RapidOCR 也能跑。
- **改版（2026-10-13）**：原本映像要安裝 Tesseract 與語言檔，改用 RapidOCR 後不再安裝。

## 使用者做的決定

- 作品用 trace.moe、圖片文字用 OCR，角色不辨識；全部免費。
- 修改用右鍵選單加預填表單，不用回覆訊息的方式。
- 分隔符號統一為「、」。
- 欄位順序：作品、圖片文字、角色、關鍵字。
- 辨識失敗要明顯標示，並提供「重新辨識」，只補失敗的欄位。
- 舊圖片不重新處理，但要能被搜尋（用整段訊息文字）。
- 使用者端的行為：/search 的提示與公開發圖、勾選頻道、預設全選，都照上面寫的內容。
- 可用頻道要求使用者看得到該頻道。
- 離線期間的圖片要補處理，用設定時間點區分新舊。
- 只處理圖片附件（含 GIF）與圖片網址（2026-10-19 起，見上方「哪些訊息要處理」）；有非圖片附件的訊息整則不動；一般網頁連結不處理。
- 辨識完才發圖片訊息。
- 圖片訊息加上「上傳者」一行。
- 用 Docker 部署並提供 Dockerfile。

## 實作期間的設計變更（2026-10-16 同步）

以下為實作期間使用者改變或新增的重要設計，詳細決定與理由見 `docs/plans/2026-10-12-image-bot.md` 的「使用者的回答」「追加決定」「試驗結果與決定」各節。

- **OCR 改用 RapidOCR**（2026-10-13）：原因與做法見「二、辨識」。部署機記憶體小，辨識一張圖約數秒（滿版漫畫頁可達數分鐘，單張逾時 3 分鐘）。
- **日文辨識**（2026-10-13，Pi 第四版試驗）：中文模型讀不出假名，加入日文辨識模型，依是否含假名選用結果。
- **漫畫與直式圖片整張辨識**（2026-10-13）：使用者的圖片除了動畫字幕截圖，還有漫畫（直書對話框）與電視節目截圖；字幕區沒字、有直書框或圖片高 > 寬時改辨識整張。trace.moe 對漫畫與真人截圖找不到作品，作品欄標失敗屬預期。
- **一次只處理一則訊息**（2026-10-14）：為避免 Pi 記憶體不足，來源頻道的訊息排隊依序處理，輪到時才下載；同時只解碼一張原圖。排入佇列時在原訊息加 ⏳。
- **處理失敗的標示**（2026-10-14）：任一張下載失敗則一張都不發；發送失敗時已發出的保留；兩者都不刪原訊息，移除 ⏳ 改加 ❌，不在頻道說明原因。帶 ❌ 的原訊息啟動補處理時不再處理。上傳者與原文中的 mention 一律不通知。
- **❌ 原訊息可「重新辨識」**（2026-10-14）：對帶 bot ❌ 的使用者原訊息使用「重新辨識」，會重新處理整則訊息（同自動處理流程）。
- **編輯表單只套用改過的欄位**（2026-10-15）：避免與同時進行的重新辨識互相覆蓋；失敗欄位預填 `⚠️ 辨識失敗`，送出空白即清空。
- **可用頻道需要「讀取訊息歷史」**（2026-10-15）：可用條件除了「檢視頻道」，還要有「讀取訊息歷史」權限（`/search`、`/sources`、右鍵指令皆同）。權限計算自行移植 discordgo 的成員權限計算（v0.29.0 未公開 `MemberPermissions`）。
- **`/sources`**（2026-10-16）：勾選搜尋頻道的指令名稱為 `/sources`，可用於伺服器與私訊；變更即儲存；可選 0 個（搜不到任何東西），但使用者勾選的頻道全部被移除而變成 0 個時視為沒選過（預設全部）；之後新增的來源頻道不自動加入；最多列 125 個頻道。
- **搜尋**：不比對 `⚠️ 辨識失敗`；不分大小寫、全半形統一、多詞須全部符合；依命中欄位等級與新舊排序。
- **設定的自動清理**：來源頻道被刪除、bot 被踢出伺服器（含離線期間）時，自動從設定移除。
- **啟動讀取儲存頻道失敗**：記 log 後以空資料啟動。
- **環境變數**：新增選填的 `TRACEMOE_KEY`、`TRACEMOE_MIN_SIMILARITY`（預設 0.90）、`MEMBER_CACHE_TTL`（預設 5 分鐘）。


## 圖片網址訊息支援（2026-10-19 同步）

詳細規則與決定見 `docs/plans/2026-10-19-image-url.md`（文末「使用者的回答」「把關後的決定」各節，越後面越新）。

- **圖片網址**：訊息文字中的 http/https 連結（抽取比照 Discord 自動連結；`<網址>`、`||網址||`、`[文字](網址)` 都算，同一網址只算一張），路徑副檔名為 .png/.jpg/.jpeg/.webp/.gif，或 Discord 對它產生的預覽是圖片（type image/gifv，或預覽的 image/thumbnail 就是該網址）。一般網頁連結照舊不處理。附件在前、網址在後一起編號；含非圖片附件的訊息照舊整則不處理。
- **新舊區分**：附件訊息（含附件與網址混合）只看設定時間點；只含圖片網址的訊息看 max(設定時間點, `url_since`)。`url_since` 是「圖片網址功能上線時間點」，存在設定資料中；新版第一次啟動（設定成功讀取時）於 READY 後寫入，值為寫入儲存頻道時 Discord 回傳的訊息 ID（Discord 伺服器時間，不用本機時鐘）。寫入失敗或設定讀取失敗時不寫，只含圖片網址的訊息一律當舊訊息。
- **舊訊息**：收進搜尋，比對與提示文字去掉圖片網址；去掉後沒有文字的不收錄。部分的編輯事件會重讀完整訊息再更新索引。
- **新訊息**：下載網址圖（gifv 不處理；預覽圖片在別的網址時下載預覽中的圖片網址），必須能解碼成 PNG/JPEG/GIF/WEBP，重新上傳（劇透保留 `SPOILER_`），關鍵字為去掉圖片網址後的文字；任一張失敗就一張都不發、保留原訊息加 ❌。含尚無預覽的連結時等 5 秒重讀再判定；預覽補上或使用者編輯加入圖片網址（MESSAGE_UPDATE）也會觸發處理。重讀後已沒有圖片時不發、不刪、不加 ❌；只剩 gifv 的 ❌ 訊息「重新辨識」回「這則訊息沒有可處理的圖片」且不加回 ❌。
- **網址下載安全（防 SSRF）**：只接受 http/https、不可帶帳密；只連公開位址的 80、443（擋 loopback、私有、link-local、多播、CGNAT、保留段與內嵌 IPv4 的 IPv6 過渡位址），以實際連線 IP 檢查並涵蓋每一跳轉址（最多 5 跳）；不使用代理；25MiB 上限、逾時 2 分鐘；固定 User-Agent。
- **`/search` 貼網址圖**：同附件排隊；重讀訊息確認網址仍在原位置（且作者不是 bot/webhook），再以同一安全下載器檢查（15 秒逾時，只讀標頭與前 512 bytes 內容嗅探）：
  - 確定已刪除（404、410、轉址到 imgur removed.png）或確定不是圖片（網頁等）→ ephemeral「圖床上的圖片已被刪除，無法貼出」並移除該筆。
  - 內容確定為 PNG/JPEG/GIF/WEBP → 公開貼出網址（劇透時為 `||網址||`，mention 不通知；不下載、不重新上傳）。
  - 其他（403 等非 200、被安全規則擋下、逾時、SVG 等非這四種格式、多個或無法解析的 Content-Type、`Refresh` 標頭、非 inline 且檔名不是圖片副檔名的 `Content-Disposition`、無法解析的 `filename*`、未解壓的 Content-Encoding）→「無法確認」：只有該訊息中 Discord 對此網址產生了圖片預覽（type image/gifv）才照樣貼出，否則回「目前無法確認圖片，請稍後再試」、不移除索引（防止散播偽裝成圖片網址的釣魚連結）。
- **已知限制**：需要 Referer 或登入的圖床會下載失敗；過期的 Discord 附件連結無法下載或預覽；依 UA/IP 回不同內容的釣魚伺服器無法防範。
