# 動畫截圖圖庫 bot 實作規劃

> **給實作者：** 依 `superpowers:test-driven-development` 逐項實作，步驟用 `- [ ]` 追蹤。依專案規則，實作者不 commit；每個「交付點」由 PM 決定是否 commit（見待決定問題 Q8）。

**目標：** 把現有只會記住頻道的 bot，改成「圖片來源頻道自動整理圖片＋辨識作品與字幕＋右鍵修改＋跨伺服器 `/search`」，設定存在 Discord 儲存頻道，用 Docker 部署。

**架構：** `bot.go` 只負責讀設定、建立 session、接線。功能拆成 `internal/` 下的小套件，每個套件只依賴「自己定義的小介面」（Discord、HTTP、trace.moe、OCR、時鐘），`*discordgo.Session` 與 `*discordgo.State` 直接滿足這些介面；測試一律用假實作，`go test ./...` 不連網、不需要 Python／RapidOCR。OCR 由同一容器內常駐的 Python 子行程（RapidOCR）執行，Go 以 stdin/stdout JSON lines 溝通（見「OCR 改版修訂」，架構依 Q54）。

**技術：** Go（go.mod 原為 `go 1.24.13`，階段 11 依使用者決定升級為 `go 1.27.0`）、discordgo v0.29.0、godotenv、`golang.org/x/image/webp`（新依賴，解 WEBP）、RapidOCR（rapidocr_onnxruntime 1.4.4，Python 3.12）＋ OpenCC、trace.moe REST API、Docker（部署目標 Raspberry Pi 3B，linux/arm64）。

**設計文件：** `docs/superpowers/specs/2026-10-12-image-bot-design.md`（實作者兩份都要讀）

**標記說明：** 文中 `Q數字` 指本檔最後「待決定問題」。標了 Q 的地方在使用者回答前**不得實作**；回答後 PM 會把答案填回本檔或附在派工訊息中。

## 全域限制

- 全部免費：不得引入付費 API。
- 辨識失敗標記字串固定為 `⚠️ 辨識失敗`。
- 圖片訊息欄位順序：作品、圖片文字、角色、關鍵字；留空欄位放最後；最後一行 `上傳者：<@userID>`，不可編輯、不參與搜尋。
- 多值分隔一律輸出「、」；圖片文字不拆分，多句用換行。
- 處理的附件類型：PNG、JPG、WEBP、GIF（GIF 用第一格）。訊息含任何非圖片附件 → 整則不處理不刪除；只有連結/embed 不處理；純文字不處理。
- 全部辨識完成才發圖片訊息；每張圖一則；重新上傳檔案；全部發完才刪原訊息。
- 設定只能存成 Discord 訊息（JSON，>2000 字拆多則），不得寫檔。
- 不得覆蓋使用者已填資料（重新辨識只動失敗欄位）。
- 可用頻道 = 被設為來源 ∧ 使用者是該伺服器成員 ∧ 使用者對該頻道有 View Channel（含身分組與頻道覆寫）。套用在 `/search`、勾選指令、右鍵指令。
- 不開 Server Members 特權 intent；Intents 為 `IntentsGuilds | IntentsGuildMessages | IntentsMessageContent`。
- 成員查詢快取 key（guildID, userID），404 也快取，mutex 保護，預設 5 分鐘（Q49）。頻道可見性不快取，用 gateway state 現算。
- 新環境變數 `STORAGE_CHANNEL_ID`（必填）。
- OCR：RapidOCR（PaddleOCR 中文手機版模型）＋ OpenCC 簡轉繁（設定依 Q58）；OCR 必須是可替換介面。
- 部署機記憶體很小（Pi 3B，905MB RAM）：同一時間只解碼一張原圖、原圖產生縮圖後立即釋放；OCR 與 trace.moe 各自排隊（並行數 1）。
- trace.moe 請求要排隊（並行數 1）。
- 每次執行 `go build ./...`、`go vet ./...`、`go test ./...` 都要通過。

## 把關重點（Review Focus）

測試未必能自然覆蓋、但最容易傷到使用者的情況，各自已在負責的任務加上釘住它的測試：

1. **圖片遺失**：多張圖中任一張下載/辨識/發送失敗，或刪原訊息失敗時，原圖不能消失（Task 5.2 `TestProcess_SendFailure_KeepsOriginal`）。
2. **覆蓋使用者資料**：使用者編輯與「重新辨識」同時發生時，重新辨識不能把使用者剛填的欄位蓋掉（Task 8.2 `TestRerecognize_MergesIntoLatestContent`）。
3. **繞過權限**：`/search` 送出的值是 client 傳來的字串，可被偽造；送出時要重新檢查頻道可用（Task 9.2 `TestSearchSubmit_RejectsUnavailableChannel`）。
4. **啟動讀設定失敗後被空資料覆蓋**：讀取失敗不可接著寫入空資料（Task 1.3 `TestLoad_ErrorDoesNotAllowSave`）。
5. **非指令類 interaction 造成 panic**：現有 handler 對所有 interaction 呼叫 `ApplicationCommandData()`，modal / component / autocomplete 會 panic（Task 2.1 `TestRouter_DispatchesByInteractionType`）。

其他風險（給把關者）：

- **並行**：discordgo 每個事件開 goroutine，`store`、`index`、成員快取一定要上鎖，測試用 `go test -race`。
- **圖片訊息解析**：OCR 文字裡若出現「角色：」等開頭的行，解析會切錯欄位（Task 3.1 `TestParse_TextContainingLabelLikeLine` 規定只認「行首的已知標籤且順序在後」）。
- **2000 字上限**：Format 結果必須 ≤ 2000 字（Q23）。
- **autocomplete 3 秒**：未快取伺服器的成員查詢要並行且有截止時間（Q51）。
- **CDN 連結過期**：索引不存附件 URL，貼圖前重新抓訊息取得新 URL。
- **`discordgo.memberPermissions` 未匯出**：v0.29.0 沒有公開的 `MemberPermissions`，需自行移植權限計算（Task 7.1）。
- **全域指令**：使用者安裝指令只能全域註冊，全域指令傳播較慢；不要在關機時刪掉（Q2）。
- **OCR 子行程**（Task 4.3）：worker 卡住、當掉、stdout 混入非 JSON 輸出、回應錯位（上一張逾時的回應被下一張讀到）都必須不影響後續圖片；逾時一律殺掉 worker、下次重啟，不可重用可能殘留回應的管線。bot 結束時 worker 也要結束（不留殭屍行程）。
- **記憶體**（Task 5.1）：多則訊息同時到達時，不可同時持有多張解碼後的原圖；排隊等 OCR／trace.moe 的只能是縮圖。
- **排隊時間與 interaction 時效**（Task 8.2）：每張 OCR 約 15～20 秒，排隊可能很長；deferred interaction 的 token 只有 15 分鐘，逾期後 `InteractionResponseEdit` 會失敗，要記 log、不可 panic（優先順序依 Q62）。

**縮小演算法：** `golang.org/x/image/draw.CatmullRom`（會依縮小比例擴大取樣範圍，效果接近 OpenCV `INTER_AREA`；不可用 `ApproxBiLinear`／`NearestNeighbor`，縮小時會產生鋸齒）。與 spike 的 OpenCV 結果不會逐位元相同，所以準確度以整合測試為準。

**worker 協定（stdin/stdout，每行一個 JSON）：**
- worker 啟動、模型載入完成後輸出 `{"ready":true}`。
- 請求：`{"id":<遞增整數>,"png":"<base64 PNG>"}`。
- 回應：`{"id":<同 id>,"items":[{"box":[[x,y]×4],"text":"<已簡轉繁>","score":0.97}]}` 或 `{"id":<同 id>,"error":"<訊息>"}`（單張失敗不結束 worker）。
- stdout 只能有協定輸出；所有記錄寫 stderr（Go 端轉到 log）。
- worker 讀到 EOF 就結束。

**Go 端 `RapidOCR` 行為：**
- 第一次 `RecognizeText` 才啟動 worker（`exec.Command`，**不用** `CommandContext`，生命週期由 `RapidOCR` 管），等 `{"ready":true}`，超過 `StartTimeout` → 殺掉、回錯誤。
- 內部 mutex，同時只送一張（呼叫端另有排隊，見 Task 4.4）。
- 回應 `id` 不符、JSON 錯誤、worker 結束、逾時（`Timeout` 或 ctx 結束）→ 殺掉 worker（`Process.Kill` + `Wait`）、回錯誤；下一張重新啟動。
- `items` 為空或組行後為空字串 → `ErrNoText`。
- 預處理後寬或高 < 2px → 直接 `ErrNoText`，不送 worker。
- `IdleTimeout` > 0 時，最後一張完成後閒置超過該時間就關閉 stdin 讓 worker 結束（依 Q55）。

**組行（`JoinOCRItems`）：** 依 box 垂直中心排序；與目前行的垂直範圍重疊 ≥ 較矮者高度 50% 視為同一行；同行依 x 排序以空白連接；行與行以 `\n` 連接；最後套 `CleanOCRText`（中日文字間空白會被移除，英文保留）。信心度過濾依 Q66。

- **Q20 「上傳者」mention 是否通知對方**：mention 預設會通知（ping）原發文者；編輯訊息時也可能再次觸發。｜使用者可見。｜建議：不通知（只顯示）。

- **Q23 超過 2000 字**：Discord 訊息上限 2000 字，OCR 或原文很長時會發送失敗。｜要決定截掉哪裡。｜建議：先截圖片文字、再截關鍵字，被截處結尾加「…」。編輯表單送出時超過則回覆錯誤、不修改。

### 架構要點

- **呼叫方式（建議，Q54）**：同一容器內常駐 Python 子行程，stdin/stdout JSON lines。理由：模型只載入一次（省每張 3 秒）、不需開 port 或 HTTP 框架、維持 Q6 的單一 `docker run`；比 sidecar 少一個容器與網路設定。
- **前處理分工**：Go 端做裁切與縮小（只解碼一次，原圖不送進 Python，Python 端記憶體更少，送出的 PNG 只有約 640x126）；Python 端只做 RapidOCR 與 OpenCC（OpenCC 已在 spike 驗證，Go 端沒有同等成熟的套件）。組行與清理在 Go 端，方便不裝 Python 就能測試。
- **Q17/Q18 原前處理的處置**：裁下方 35% 保留；**灰階刪除**（RapidOCR 吃彩色圖，spike 未灰階即 100%）；**放大 2 倍改為縮到寬 640**（spike 驗證值，且 RapidOCR 偵測階段本身會縮放）；長邊 2000px 上限不再需要；整張重試改由 Q57 決定；`CleanOCRText` 保留。
- **方向分類與執行緒（技術建議）**：字幕不會上下顛倒，建議關閉 cls；Pi 3B 4 核心，`intra_op_num_threads=4`。最大的疑點是偵測預設把短邊放大到 736（見 Task 4.0），建議改 `det_limit_type=max`。三者都要在 Pi 上量過才定（Q53）。
- **記憶體預算（估計，待 Task 11.1 用 `docker stats` 實測）**：Pi 可用約 525MB RAM + zram。OCR worker 峰值約 600MB（重測後可能大幅下降）；Go bot 閒置約 20～40MB，加上一張解碼中的原圖（16M 像素 RGBA ≈ 64MB，Q60）、每則處理中訊息的原始附件 bytes（每個 ≤ 25MB，重新上傳需要）。同時只解碼一張、原圖用完即丟，排隊中只持有縮圖（每張約 1～2MB）。
- **共用解碼**：`Pipeline.Recognize` 解碼一次，同時產生 trace.moe 用的長邊 1000px PNG 與 OCR 用的寬 640 字幕條，之後原圖可被 GC。
