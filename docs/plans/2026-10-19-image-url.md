# 圖片網址訊息支援 實作規劃

> **給實作者：** 依 `superpowers:test-driven-development` 逐項實作，步驟用 `- [ ]` 追蹤。依專案規則實作者不 commit，由 PM 在流程最後 commit。標了 `U數字` 的地方要等使用者回答（見文末「待決定問題」）；回答前**不得實作那一部分**，PM 會把答案填回本檔或附在派工訊息中。

**目標：** 圖庫頻道中「圖片網址＋文字」的訊息也能被搜尋與處理：舊訊息收進索引（`/search` 直接貼網址），新訊息下載網址圖片、走一般辨識流程後重新上傳並刪原訊息。

**架構：** `internal/recognize` 新增「訊息中的圖片清單」（附件＋圖片網址，依編號順序）取代只看附件的 `Eligible`；`internal/pipeline` 新增防 SSRF 的網址下載器，`process` 改為逐「圖片來源」下載；`internal/index` 的 `Key`／`Entry` 加上「網址圖」；`/search` 選到網址圖時只重讀訊息確認、直接貼網址。embed 是非同步產生的，所以新訊息「含尚無法判定的網址」時延後重讀，並新增 MESSAGE_UPDATE 觸發處理。

**技術：** Go 1.27、discordgo v0.29.0、標準庫 `net`／`net/netip`／`net/http`／`net/url`（不新增依賴）。

**設計文件：** `docs/superpowers/specs/2026-10-12-image-bot-design.md`（原規則「貼圖片連結或 embed 的訊息不處理」由本規劃取代）；舊規劃 `docs/plans/2026-10-12-image-bot.md`。

## 已定案的需求（PM 轉述，使用者已確認）

1. 舊訊息（設定時間點之前、使用者發的）含圖片網址者收進索引；每個圖片網址算一張，附件與網址混合時一起算「（第 N 張）」。
2. 搜尋比對與提示文字去掉圖片網址；去掉後沒有其他文字的不收錄。
3. `/search` 選到網址圖：公開訊息內容就是該網址，不下載、不重新上傳。附件圖照舊重新上傳。
4. 新訊息（設定時間點之後，含補處理）：下載網址圖片，走一般辨識流程，每張發一則「重新上傳圖片＋圖片訊息」，全部成功才刪原訊息；關鍵字為去掉圖片網址後的原訊息文字；任一張下載失敗（已刪除、不是圖片、超過 25MiB）→ 一張都不發、保留原訊息、加 ❌。對 ❌ 原訊息「重新辨識」也適用。
5. 圖片網址判定：Discord 對該網址的 embed 為圖片（type `image`／`gifv`，或 embed 的 image／thumbnail 網址與該網址相同），或網址路徑結尾為 `.jpg/.jpeg/.png/.webp/.gif`（不分大小寫、忽略 query）。一般網頁連結不算，照舊不處理。
6. 安全：只接受 http/https；擋 loopback、私有、link-local、多播、未指定等位址，以實際連線 IP 檢查（防 DNS rebinding）；每一跳重新導向都檢查；25MiB 上限；有下載逾時；內容必須是圖片。

## 全域限制

- 全部免費：不得引入付費 API；不新增 Go 依賴。
- 附件判定規則不變：訊息含任何非圖片附件 → 整則不處理（就算有圖片網址）。
- 全部下載成功才辨識；全部發出成功才刪原訊息；任何失敗都保留原訊息並加 ❌（關機中斷除外）。
- 原圖同時只解碼一張；trace.moe／OCR 排隊不變。
- 網址下載上限 `pipeline.MaxAttachmentSize`（25 << 20）。
- 發出的訊息一律 `AllowedMentions{Parse: []}`（含 `/search` 貼網址）。
- `go build ./... && go vet ./... && go vet -tags rapidocr ./...`、`go test ./...`、`CGO_ENABLED=1 go test -race ./...` 每個任務結束都要通過；測試不得連外網（`httptest` 伺服器只在 127.0.0.1）。

## 把關重點（Review Focus）

測試最不容易自然覆蓋、但最容易傷到使用者的五件事；每項都已在負責的任務加了釘住它的測試：

1. **SSRF**：網址指向 127.0.0.1、10.x、169.254.169.254、`[::1]`、IPv4-mapped IPv6、解析到私有位址的網域名、或公開網址 302 轉到私有位址，都必須在**連線前**被擋（Task 2 `TestURLFetch_BlocksPrivateTargets`、`TestURLFetch_BlocksRedirectToPrivate`、`TestURLFetch_ChecksResolvedIP`）。
2. **刪原訊息前必須全部成功**：多張中任一網址下載失敗、不是圖片、超過 25MiB → 不發任何一則、不刪、加 ❌；補處理重讀後訊息已沒有任何圖片（使用者把網址編輯掉）→ 不發、**不刪**、不加 ❌（Task 5 `TestProcess_URLFailure_SendsNothingKeepsOriginal`、`TestProcess_NoSourcesAfterRefetch_DoesNotDelete`）。後者也修掉現有的潛在問題：補處理重讀後附件被移除時，現行程式會直接刪原訊息。
3. **embed 非同步**：MESSAGE_CREATE 時沒有副檔名的網址常常還沒有 embed。不能在 create 時就把它當「不是圖片」處理掉（其他圖發出後原訊息被刪，那張圖就遺失）；也不能因 create 與 update 都觸發而處理兩次（Task 5 `TestHandleMessage_UnresolvedLinkWaitsThenRefetches`、`TestHandleMessageUpdate_EmbedArrives_ProcessesOnce`）。
4. **Key 偽造與相容**：`/search` 收到的 `c:m:uN` 由 client 傳來，仍要經過頻道權限檢查；貼出前重讀訊息，網址已不在該位置就回「找不到這張圖片」並移除該筆；舊格式 `c:m:N` 照舊代表附件（Task 3 `TestParseKey_LinkAndLegacyFormats`、Task 6 `TestSearchSubmit_LinkEntry_URLChanged_Gone`）。
5. **舊訊息編輯事件**：部分更新（沒有 attachments／embeds 資訊）不能誤刪或留下過時網址；把網址編輯掉要移除那一張（Task 4 `TestMessageUpdated_LegacyPartial_RefetchesFull`、`TestMessageUpdated_LegacyLinkRemoved`）。

其他風險（給把關者）：

- **mention**：網址裡可能含 `@everyone` 字樣；`/search` 的 `InteractionResponseEdit` 必須帶 `AllowedMentions{Parse: []}`。
- **embed 網址比對**：Discord 回傳的 embed.URL 可能與使用者打的字不完全相同（百分比編碼、大小寫）。單元測試只能測我們假設的格式；Task 7 有在 Pi 上用真實訊息驗證的步驟。
- **記憶體**：與附件相同，一則訊息的所有圖片會同時在記憶體（每張最多 25MiB）；沒有比現在更差，但網址圖沒有事先知道大小，要靠 `Content-Length` 先擋與 `LimitReader`。
- **代理環境變數**：網址下載器的 Transport 必須 `Proxy: nil`，否則 Control 檢查到的是代理伺服器的 IP。
- **既有測試修改**：Task 4 會改變舊訊息部分更新的行為（改為重讀），`internal/index` 中相關的既有測試要跟著調整；把關者要確認調整的是預期行為，不是把失敗的斷言刪掉。

```go
// Link 是訊息文字中的一個 http/https 連結（依出現順序、同一網址只留第一個——U6）。
type Link struct {

    Start, End int    // 在 content 中要被移除的位元組範圍（含 <>、||、[文字](...) 等包裝——U7）

}
func Links(content string) []Link

// ImageSource 是訊息中的一張圖，依編號順序（U8：建議附件在前、網址在後）。
type ImageSource struct {
    Attachment *discordgo.MessageAttachment // 附件圖；網址圖為 nil
    Index      int    // 附件圖：在 m.Attachments 的位置；網址圖：在 Links(m.Content) 的位置

    FetchURL   string // 網址圖：要下載的網址（U4；預設等於 URL）
    Spoiler    bool
}
func (s ImageSource) IsLink() bool

// ImageSources 回傳訊息中所有圖片；訊息含非圖片附件時 ok=false（整則不處理）。
func ImageSources(m *discordgo.Message) (srcs []ImageSource, ok bool)
// Eligible：ok && len(srcs) > 0。
func Eligible(m *discordgo.Message) bool
// UnresolvedLinks：有連結既不是副檔名圖片、也沒有任何 embed 的 URL 與它相符（Discord 可能還沒產生預覽）。
func UnresolvedLinks(m *discordgo.Message) bool
// TextWithoutImageURLs：m.Content 移除所有「圖片網址」的 Link（套用 Keep）後 TrimSpace；一般網頁連結保留。
func TextWithoutImageURLs(m *discordgo.Message) string
```

圖片網址判定（需求 5）：
- 網址 `url.Parse` 成功、scheme 為 `http`／`https`、有 host。
- 副檔名：`strings.ToLower(path.Ext(u.Path))` 在既有 `imageExtensions`。
- embed：有一個 embed 滿足「`sameURL(e.URL, link)` 且 type 為 `image` 或 `gifv`」或「`e.Image.URL`／`e.Thumbnail.URL` 與 link `sameURL`」。`sameURL`：字串相同，或兩者 `url.Parse` 後 `String()` 相同。

## Task 2：防 SSRF 的網址下載器（pipeline）

**Files:**
- Create: `internal/pipeline/urlfetch.go`、`internal/pipeline/urlfetch_test.go`

**Interfaces — Produces：**

```go
// ErrBlockedAddress 表示連線目標不是公開位址（或 port 不允許——U10）。
var ErrBlockedAddress = errors.New("blocked address")
// CheckPublicAddr 回傳 ap 是否可連線；不可時回包含 ErrBlockedAddress 的錯誤。
func CheckPublicAddr(ap netip.AddrPort) error
// URLFetcher 下載使用者貼的圖片網址；滿足 Fetcher。
type URLFetcher struct { /* client *http.Client; maxBytes int64 */ }
func NewURLFetcher() *URLFetcher                                 // 正式用：CheckPublicAddr
func newURLFetcher(check func(netip.AddrPort) error) *URLFetcher // 測試用：可放行 httptest 的 127.0.0.1:port
func (f *URLFetcher) Fetch(ctx context.Context, rawURL string) ([]byte, error)
```

規格：
- `CheckPublicAddr`：先 `Unmap()`；擋 `IsLoopback`、`IsPrivate`、`IsLinkLocalUnicast`、`IsLinkLocalMulticast`、`IsInterfaceLocalMulticast`、`IsMulticast`、`IsUnspecified`，以及前綴 `0.0.0.0/8`、`100.64.0.0/10`、`192.0.0.0/24`、`198.18.0.0/15`、`240.0.0.0/4`（含 255.255.255.255）、`64:ff9b::/96`、`2001:db8::/32`。port 依 U10（建議只允許 80、443）。
- Transport：`Proxy: nil`；`DialContext` 用 `net.Dialer{Timeout: 10s, Control: ...}`，Control 把 `address` 解析成 `netip.AddrPort` 後呼叫 check（每次實際連線都檢查，含重新導向與 keep-alive 新連線）；`ResponseHeaderTimeout: 30s`；`MaxResponseHeaderBytes: 64KiB`。
- Client：`Timeout: 2 * time.Minute`（沿用附件）；`CheckRedirect`：最多 5 跳、每跳 scheme 必須 http/https、URL 不得帶帳密。
- 請求前檢查：scheme http/https、有 host、沒有 userinfo；`User-Agent` 設為固定字串（技術建議 `discord-imageCR-bot`）。
- 回應：非 200 → 錯誤；`Content-Length` > maxBytes → `ErrTooLarge`（不讀 body）；`Content-Type` 有值且不是 `image/*`、也不是 `application/octet-stream` → `ErrNotImage`（不讀 body）；body 以 `LimitReader(max+1)` 讀，超過 → `ErrTooLarge`。
- 是否真的是圖片（能解碼）在 Task 5 檢查，`ErrNotImage` 定義在 `urlfetch.go` 供兩處共用。

## 待決定問題（需問使用者）

以下都會影響使用者看得到的行為；每題附建議，但**不得**在回答前實作。

**U1. 部署後第一次啟動：設定時間點之後、以前被忽略而留在頻道中的圖片網址訊息怎麼辦？**
- 原因：啟動掃描無法分辨「離線期間發的」與「以前規則不處理、一直留著的」。照需求 4，這些訊息在第一次啟動時就會被補處理：發成圖片訊息、**刪除原訊息**。
- 影響：可能一次大量處理（每張 OCR 約 15～20 秒）並刪除使用者以前發的原訊息；下載失敗的會被加 ❌。
- 選項：(a) 照補處理；(b) 只收錄進搜尋、不處理（需要另外記錄「本功能上線時間點」，例如存進儲存頻道的設定資料，會改到資料模型）。
- 建議：(a)，與「設定時間點之後的圖片一律整理」一致、不改資料模型；但會刪原訊息，必須由使用者決定。

**U2. 設定時間點之後的文字訊息，被使用者「編輯」加上圖片網址時，要不要處理？**
- 原因：embed 是以 MESSAGE_UPDATE 補上的，本規劃已需要處理更新事件；同一機制也會讓「編輯加入網址」觸發處理。
- 影響：(是) 編輯後幾秒內被處理、原訊息刪除；(否) 只靠 embed 補上的更新觸發，編輯加入的網址要等下次 bot 重啟補處理時才被處理（重啟時無法分辨是否編輯過）。
- 建議：是（否的話也會在下次重啟處理，行為反而不一致）。

**U3. 新訊息中的 gifv（Tenor、Giphy、imgur `.gifv` 等動圖連結）怎麼處理？**
- 原因：gifv 的網址是網頁或影片，不是圖片檔；能下載的只有 embed 的靜態縮圖。
- 影響：(a) 下載縮圖重新上傳：動畫變成靜態圖，且原訊息被刪；(b) 新訊息不把 gifv 當圖片：照舊不處理（保留原狀、不加 ❌），舊訊息仍收進搜尋、`/search` 貼網址仍會動；(c) 當成下載失敗：加 ❌。
- 建議：(b)。

**U4. embed 判定為圖片（type `image`），但使用者貼的網址是網頁、真正的圖片網址在 embed 的 image／thumbnail（例如 imgur 單張圖片頁）時，新訊息要下載哪裡？**
- 影響：(a) 下載 embed 中的圖片網址（同樣經過 SSRF 檢查）：通常能成功；(b) 下載 Discord 代理網址（`proxy_url`，圖片已經過 Discord 縮放，可能不是原圖畫質）；(c) 只下載使用者貼的網址：網頁不是圖片 → ❌。舊訊息不受影響（`/search` 一律貼原網址）。
- 建議：(a)。

**U5. 網址內容是圖片但不是 PNG／JPG／WEBP／GIF（AVIF、SVG、BMP、HEIC 等）時，新訊息怎麼辦？**
- 原因：辨識只支援這四種格式，與附件規則相同。
- 影響：(a) 當成「不是圖片」：一張都不發、加 ❌；(b) 仍重新上傳，作品與圖片文字標辨識失敗。舊訊息以副檔名判定時本來就只收這四種；以 embed 判定的照收（`/search` 只貼網址）。
- 建議：(a)，與附件「只處理這四種」一致。

**U6. 同一個網址在一則訊息中出現兩次，算一張還是兩張？**
- 建議：一張（Discord 也只顯示一個預覽）。

**U7. 這些寫法算不算圖片網址、去掉網址後文字怎麼留？**
- `<https://…jpg>`（使用者刻意不顯示預覽）——建議：算；整段（含 `<>`）去掉。
- `||https://…jpg||`（劇透）——建議：算；新訊息重新上傳時保留劇透（檔名加 `SPOILER_`），`/search` 貼出 `||網址||`。
- `[文字](https://…jpg)`（遮罩連結）——建議：算；去掉網址、保留「文字」。
- 影響：搜尋得到哪些圖、新訊息的劇透是否被公開、關鍵字內容。

**U8. 附件與網址混在同一則訊息時的編號順序（PM 授權規劃者建議，可由 PM 直接決定）**
- 建議：附件在前（依附件順序）、網址在後（依文字中出現順序）——與 Discord 顯示順序相同（附件顯示在預覽之前）。訊息本身無法得知附件與文字的相對位置。

**U9. 含「尚無預覽的連結」的新訊息要等多久再判定？**
- 原因：Discord 通常 1～3 秒內補上 embed，但不保證。
- 影響：等待期間訊息沒有 ⏳；等太短，慢一點產生預覽的圖片網址會被當一般連結（與其他圖同在一則時，那張不會被發出、網址留在關鍵字中；只有它一張時，embed 補上的更新事件仍會觸發處理）；等太長，每則含網址的訊息都慢。
- 建議：5 秒。

**U10. 網址下載只允許標準連接埠（80、443）嗎？**
- 影響：(是) `https://example.com:8443/x.jpg` 這類網址下載失敗 → ❌；可減少探測內網服務的風險。(否) 任何連接埠都可（IP 仍會被檢查）。
- 建議：是。

**U11. `/search` 貼網址時要不要跟附件一樣排隊（同時只貼一張）？**
- 影響：網址圖不下載、不佔記憶體；排隊只會讓使用者在別人貼大圖時多等。
- 建議：不排隊。

**U12. 這些已知限制是否接受？（不需實作，只需使用者知悉）**
- 需要 Referer 或登入的圖片網站（例如 pixiv 原圖網址）會下載失敗 → ❌。
- 以前貼在訊息裡的 Discord 附件連結（`cdn.discordapp.com/...?ex=...`）簽章可能已過期：新訊息下載會失敗 → ❌；舊訊息 `/search` 貼出的網址可能顯示不出預覽。
- `/search` 貼出網址後，如果原圖已被圖床刪除，公開訊息只會是一個網址、沒有預覽（bot 不會先檢查）。

## 使用者的回答（2026-10-19，已定案）

- **U1：選 (b)**。新增「圖片網址功能上線時間點」（store 全域欄位，例如 `url_since`，snowflake 或時間）。新版第一次啟動時若沒有此欄位，以啟動當下（READY 收到時間）寫入並存回儲存頻道。只含圖片網址（沒有圖片附件）的使用者訊息：ID 早於 max(該頻道 setAt, url_since) → 只收進搜尋（舊圖片訊息），不補處理；晚於才補處理。附件訊息的規則不變（只看 setAt）。附件與網址混合的訊息：依附件規則（看 setAt）處理整則。
- U2～U7：照規劃者建議（U2 編輯加網址要處理；U3 gifv 新訊息不處理、不加 ❌，舊的照收、/search 貼網址；U4 下載預覽中的圖片網址（同樣經 SSRF 檢查）；U5 AVIF/SVG/BMP/HEIC 等當成不是圖片，一張都不發加 ❌；U6 同一網址算一張；U7 `<網址>`、`||網址||`（保留劇透）、`[文字](網址)` 都算）。
- **/search 貼網址前要檢查圖片是否還在**（使用者新增需求）：用同一個 SSRF 安全下載器先確認（GET 讀標頭即可，或 HEAD 不支援時退回 GET 並只讀少量內容），必須先送 deferred。
  - 回應 404/410，或內容不是圖片：回 ephemeral「圖床上的圖片已被刪除，無法貼出」，並從索引移除該筆。（PM 暫定文字，依使用者原意）
  - 網路錯誤、逾時、被安全規則擋下等其他失敗：回 ephemeral「目前無法確認圖片，請稍後再試」，不移除索引。（PM 決定）
  - 確認存在才把網址貼出（不下載、不重新上傳）；因為要檢查，網址貼圖改為和附件一樣排隊（同時 1 個），以免大量並發連外——U11 因此改為排隊。
- PM 決定（技術）：U8 附件在前、網址在後；U9 等 5 秒；U10 只允許 80、443；連結抽取比照 Discord 自動連結；固定 User-Agent。

## 把關後的決定（2026-10-19）

- 使用者決定：(1) /search 只有確定已刪除（404、410、imgur removed.png）或內容確定不是圖片時才擋下並移除索引；其他錯誤（403、被擋、逾時、太大等）照樣貼出網址；(2) 帶 ❌ 但只剩 gifv 的訊息「重新辨識」回「這則訊息沒有可處理的圖片」（Reprocess 遇 errNoImages 要回可辨識的錯誤）。
- PM 決定（把關建議）：(a) 封鎖 IPv6 過渡位址 ::/96、::ffff:0:0:0/96、2002::/16、2001::/32、64:ff9b:1::/48、fec0::/10、100::/64；(b) url_since 改用 Discord 伺服器時間（例如寫入儲存頻道時回傳訊息的 snowflake ID，或 READY 相關的伺服器時間），不用本機時鐘；(c) 舊訊息部分更新重讀與刪除的競爭：寫回前在 putMu 內確認未被刪除（例如刪除時記錄 tombstone 或世代號）；(d) /search 的 Check 使用 15 秒逾時。
